# IPasswrd — Security & Threat Model

IPasswrd is a local‑first, end‑to‑end‑encrypted password manager for Windows, iOS
and Android. This document describes what the product protects, what it explicitly
does **not** try to protect against, how each component is secured, and how to
report a vulnerability.

If you are a security researcher: please read "Threat model" before filing an
issue — several "findings" are deliberate, documented trade‑offs.

---

## 1. Cryptographic design

The vault is a self‑contained, encrypted JSON blob. Encryption uses an envelope
(KEK/DEK) scheme so the master password can change without re‑encrypting data.

| Purpose | Primitive | Parameters |
|---|---|---|
| Key derivation (master password → KEK) | **Argon2id** | 64 MiB memory, t=3, p=1, 16‑byte salt, 32‑byte output. Cost is stored in the vault header and can be raised later. |
| Data key (DEK) | 256‑bit random | Generated by the OS CSPRNG. Wrapped by the KEK. |
| Vault‑key wrap, record encryption, recovery envelope, clipboard envelope | **AES‑256‑GCM** | 96‑bit random nonce per message, 128‑bit tag. |
| Recovery code | 125‑bit random (Crockford Base32, 25 symbols) | Wraps the **same** DEK in a second, independent envelope (own salt, own AAD). |
| Sync-metadata integrity (whole document) | **HMAC-SHA-256** | Key = HKDF-SHA-256 of the DEK. Authenticates the clear-text sync metadata so a cloud/account cannot roll back, delete, or brick records (see 3.6). |
| Password generator | OS CSPRNG | Rejection sampling, no modulo bias. |
| Breach check | HIBP range API (k‑anonymity) | Only the first 5 hex chars of SHA‑1 leave the device. |

**Domain separation (AAD).** Every AES‑GCM context is bound to a distinct
associated‑data string so ciphertexts cannot be moved between contexts:

- vault‑key wrap: `ipasswrd/vault-key/v1`
- recovery‑key wrap: `ipasswrd/recovery-key/v1`
- per record: `ipasswrd/record/v1/<record-id>` (binds each record to its id)
- clipboard envelope: `ipasswrd/clip/v1`
- sync-metadata MAC key (HKDF info): `ipasswrd/doc-mac/v1` (see 3.6)
- quick‑unlock (Windows Hello wrap): `ipasswrd/quickunlock/v2/<expiry>`

**Changing the master password** re‑wraps the DEK only; records are never
re‑encrypted. **Recovery** wraps the same DEK, so a lost master password can be
reset without data loss. Both properties are covered by unit tests.

## 2. Threat model

### In scope (protected)

1. **Loss or theft of the vault file** (local, cloud, or backup). Without the
   master password (or recovery code) the file is opaque. Offline brute force is
   bounded by Argon2id; the vault's own lockout counter is a UI deterrent only and
   is **not** relied upon for cryptographic security.
2. **A compromised or curious cloud provider.** Google Drive / iCloud only ever
   receive ciphertext. OAuth scope is `drive.file` (app‑created files only).
3. **Other OS user accounts on the same machine.** At‑rest secrets (cached
   session key, OAuth refresh token) are protected with Windows DPAPI
   (`CurrentUser`) / the iOS/Android Keychain, and the browser IPC pipe is
   `CurrentUserOnly`.
4. **Malicious or nosy web pages.** The browser extension only returns secrets to
   the app over an authenticated channel; the loopback HTTP bridge enforces an
   exact `Origin` (and `Host`) allow‑list, so no website can read the vault. The
   WebAuthn provider enforces the standard rpId rule (see §3.4).
5. **Remote/network attackers.** No component listens on a public interface. The
   LAN relay refuses any peer that is not on a private/link‑local/loopback range
   (see §3.3).

### Out of scope (industry‑standard exclusions)

These are **not** defended against, because no consumer password manager can once
they occur, and claiming otherwise would be dishonest:

- **Malware already running as the signed‑in user.** Such code can read process
  memory, log keystrokes, and invoke the same OS key‑release APIs the user can. It
  is game over for any password manager. Windows Hello / TPM (see §3.1) raises the
  bar (the at‑rest key requires a user‑presence gesture to release) but cannot stop
  code that waits for the user to unlock.
- **A rooted / jailbroken device, or one with a compromised OS.**
- **Physical attackers with the device unlocked and in hand.**
- **A weak master password.** Entropy of the master password is the ultimate
  ceiling on offline resistance. The app encourages a strong one and runs the
  breach check, but cannot force good choices.

## 3. Component security

### 3.1 Quick unlock (Windows) — Windows Hello + TPM

After a password unlock the session key (DEK) is cached so the master password is
not required every time. Protection is two‑layer:

1. **Windows Hello / TPM (primary).** The DEK is wrapped with a key derived from a
   signature made by a Microsoft Passport credential that lives in the TPM and is
   released **only** after a Hello gesture (face / fingerprint / PIN). No process
   can reproduce that key without the user physically passing Hello; the private
   key never leaves the TPM.
2. **DPAPI (`CurrentUser`)** on top, using a **per‑install random entropy** (stored
   DPAPI‑protected, never a constant in source), so the cache is also
   account‑bound at rest.

On machines without Hello enrolled the app falls back to a DPAPI‑only "soft" cache
(still per‑install entropy, still bounded lifetime). The cached key **always**
expires — a hard ceiling (currently 7 days), independent of the auto‑lock interval.

Locking is deliberately distinct from signing out. Manual lock and the auto‑lock timer
drop the in-memory vault but **keep** the Hello‑gated cache, so the next unlock is a
biometric gesture rather than the master password — that is what makes Hello a real
alternative to the password, not an addition on top of it. Because the cache is
TPM/Hello‑gated, keeping it across a lock does not weaken it: an attacker with the file
still needs the user's Hello gesture. A **software‑only** cache is wiped on lock instead
(nothing would gate it). The master password is required on a cold device, after the
ceiling expires, on a password change, or on explicit sign‑out — and always works if
Hello is unavailable or fails.

On iOS/Android the equivalent is Keychain / Keystore gated by Face ID / biometric,
with a 30‑day re‑authentication ceiling.

### 3.2 Browser integration (native messaging + loopback fallback)

- **Primary transport:** a `CurrentUserOnly` named pipe reached by a native‑messaging
  host. Not reachable by other OS users.
- **Fallback transport:** a loopback‑only HTTP listener on `127.0.0.1:38799`, used
  when an antivirus blocks the browser from launching the native host. It enforces
  an exact `Host` (loopback) and `Origin` (our extension id) match and CORS, so no
  website can drive it. Secrets are only returned while the vault is unlocked.
- Diagnostic logs never contain request/response bodies — only command names and a
  coarse ok/error status.

The loopback `Origin` check defends against **web pages** (its purpose). It is not
a boundary against same‑user malware, which is out of scope (§2).

### 3.3 LAN relay for phone → PC SMS codes & clipboard (port 17346)

A LAN helper lets an iPhone Shortcut forward one‑time SMS codes and clipboard text
to the PC (the phone cannot be reached by an app on iOS otherwise). Hardening:

- **Peer allow‑list:** connections are accepted only from private / link‑local /
  loopback address ranges (RFC1918, `169.254/16`, `127/8`, IPv6 ULA/link‑local).
  Routed/internet peers are refused — the relay is never internet‑facing.
- **Bearer token:** a 96‑bit random token, compared in constant time
  (`FixedTimeEquals`). Accepted in an `X-IPW-Token` header (preferred) or `?t=` for
  the limited Shortcuts client.
- **Clipboard download (`GET /clip`, PC → phone) is OFF by default** — it is the one
  route that could hand a just‑copied PC password to a LAN peer. It must be enabled
  explicitly in Settings.
- Payloads are size‑bounded; nothing from the vault is served on this channel.

**Known residual (documented trade‑off):** on the LAN the transport is plaintext
HTTP, because the iOS client is Apple Shortcuts, which cannot perform TLS or
authenticated encryption. Use this feature only on networks you trust (home Wi‑Fi,
your own phone hotspot). SMS codes are short‑lived one‑time values; the clipboard
push carries whatever you deliberately send. For a fully end‑to‑end‑encrypted
phone→PC clipboard, use the cloud channel (iCloud/Google Drive), which is sealed
with the vault key.

### 3.4 Passkeys / WebAuthn

The extension can act as a passkey (WebAuthn) authenticator backed by the vault. The
P-256 keypair is generated inside the app; the private key is stored encrypted in the
vault and used for signing in the app process, so it never enters the web page's
memory. Before signing, the app checks the bytes are a well-formed assertion whose
authData begins with SHA-256(rpId), so it can never be used as a blind signing oracle
for arbitrary data. The rpId rule below is enforced with the full Public Suffix List
(see 3.8). The provider enforces the **standard rpId rule**: a page
may only request an rpId equal to, or a registrable parent domain of, its own host.
A page on `evil.com` cannot list or sign with a `bank.com` passkey; such requests
fall back to the browser's native authenticator. Assertions also bind the real
`origin` in `clientDataJSON`, so a correct relying party rejects cross‑origin use.

### 3.5 Cloud sync

- Google Drive: OAuth 2.0 **loopback + PKCE**, scope `drive.file`. The refresh
  token is stored DPAPI‑encrypted (Windows) / in the Keychain (mobile) and is never
  synced. The vault is E2E‑encrypted before upload.
- The OAuth **client secret is not stored in source** (see "Google OAuth" below).

### 3.6 Sync integrity (anti-rollback / tamper)

The clear-text sync metadata a merge relies on -- each record's `updatedAt` and
`deleted` flag, plus the key envelope (KDF params, wrapped key, recovery envelope,
their change stamps, and the vault id) -- is authenticated by a whole-document
**HMAC-SHA-256** seal. Its key is derived from the DEK with HKDF, so only a holder of
the master password or recovery code can produce or verify it. A cloud provider or
account that can rewrite the synced file but cannot derive the DEK therefore cannot:

- **roll a record back** to an old password by re-stamping old ciphertext as current,
- **forge a deletion** with a fabricated future-dated tombstone, or
- **brick the vault** by swapping in a foreign key envelope to lock the owner out.

The seal is verified on every unlock, quick-unlock, recovery unlock, and sync merge; a
mismatch is refused (the app offers a restore from its local backup snapshots). A file
with no seal is treated as a legacy pre-seal file and tolerated only until this install
has once produced a sealed copy of that vault; from then on an un-sealed copy of the
same vault is refused, so an attacker cannot strip the seal to force the old,
unauthenticated behaviour. That "already protected" marker lives in app-private local
storage the cloud never sees. Record payloads stay independently authenticated by their
own AES-256-GCM tag (bound to the record id), so the seal and the per-record tag are two
independent checks.

### 3.7 Where the master password is entered

The master password is only ever typed on a surface a web page cannot draw over: the
extension's toolbar popup (browser chrome) or the app's own window. The in-page autofill
bubble never collects it -- a hostile site could otherwise paint a look-alike box and
harvest it. When the vault is locked the bubble simply points the user to the app/popup,
and autofill resumes the moment the vault opens.

### 3.8 Registrable-domain boundary (Public Suffix List)

Both the autofill matcher (which saved login applies to a page) and the WebAuthn rpId
rule collapse a host to its registrable domain (eTLD+1). That boundary uses the full
official **Public Suffix List** -- embedded in the app and shipped byte-for-byte to the
extension -- not a hand-curated subset. This is what keeps sibling tenants of a
multi-tenant registry apart: `evil.duckdns.org` is never treated as the same site as
`alice.duckdns.org`, and likewise for `*.ngrok.io`, `trycloudflare.com`, `*.github.io`,
`*.myshopify.com` and every other entry, so one tenant's credential can never autofill
into a sibling's page.

### 3.9 Known residuals & roadmap

- **Auto-update is not yet code-signed.** Desktop updates ship via Velopack from GitHub
  Releases over HTTPS, but the packages are not signed with a code-signing certificate,
  so the trust root is GitHub + TLS rather than a signature the app itself verifies.
  Anyone able to publish a release (or MITM a client that trusts a rogue CA) could ship a
  malicious update. Closing this needs an OS code-signing certificate; it is planned, and
  until then users should confirm releases come from the official repository.
- **Mobile quick-unlock is hardware-crypto-gated (desktop parity shipped).** On Android the
  cached session key is RSA-wrapped by a hardware-Keystore keypair whose private half requires
  user authentication per use (BiometricPrompt + CryptoObject; explicit OAEP MGF1-SHA1
  parameters for keymaster compatibility) and is invalidated by new biometric enrollment --
  verified on-device, including the invalidate -> master password -> re-arm cycle. On iOS the
  item carries SecAccessControl(BiometryCurrentSet), so re-enrolling Face ID / changing the
  finger set invalidates it the same way. Firmware that cannot release auth-bound keys
  (probed at runtime, result cached) falls back to the previous app-gated flow so no device
  loses quick unlock; the master password always remains the fallback, and biometrics can
  never lock the user out.
- **iOS clipboard has no pasteboard expiration.** A copied secret is cleared by an in-process
  timer and marked sensitive on Android, but the iOS pasteboard's own `ExpirationDate` is not
  set, so a secret copied just before the app is killed could outlive the timer. Low impact;
  a planned hardening.
- **LAN relay is plaintext on the local network** (3.3) -- a documented trade-off of the
  Apple Shortcuts client; use the cloud channel for an end-to-end-encrypted phone->PC
  clipboard.

### 3.10 Mobile autofill target verification

Android autofill (both the system AutofillService and the accessibility-based fallback for
browsers that bypass it) offers a saved login to a screen only when the target is verified,
never guessed:

- **Browser (web) fills** match a saved login to a page only by exact registrable domain on
  the full Public Suffix List, and a reported web domain is trusted only when the providing
  package is a known browser -- so a non-browser app cannot declare a foreign web domain to
  be handed that site's credential (on the fill path and on the save path).
- **Native-app fills** match only a login whose exact origin package was recorded when it was
  saved in that app. The former fuzzy brand/name matching -- which let any app named after a
  brand (e.g. `com.paypal.evil`) be offered that brand's login on one tap -- is removed.
- The accessibility fallback derives the page domain only from a node the browser labels as
  its address bar, never from arbitrary page text, and its clipboard paste fallback marks the
  value sensitive and wipes it immediately after the paste.

The mobile vault also carries the same document-integrity seal and anti-downgrade marker as
desktop (3.6): every unlock, quick-unlock, recovery unlock and sync merge on iOS/Android is
now verified, and once a device has opened a sealed vault an un-sealed copy of it is refused.
The iOS credential provider matches strictly by registrable domain via the system's own
service-identifier binding; recovery codes and copied secrets use the same auto-clearing,
sensitivity-flagged clipboard path as passwords.

## 4. Google OAuth (client secret)

A desktop OAuth client's secret is not truly confidential under PKCE, but committing
one to a public repository gets it auto‑flagged (and possibly auto‑revoked) by
Google's secret scanner. Therefore:

- The client **id** ships in source (it is public by nature).
- The client **secret** is loaded at runtime from `IPASSWRD_GOOGLE_SECRET` or a
  git‑ignored `google_oauth.json`. If absent, the token exchange is attempted
  PKCE‑only (works for OAuth clients created as the public "iOS/Android" type).

Operators should treat any previously committed secret as compromised and rotate it
in the Google Cloud console.

## 6. Recent hardening (changelog)

- **Full Public Suffix List** now backs the registrable-domain boundary for autofill and
  passkeys (was a hand-curated subset), closing a cross-tenant credential leak on
  multi-tenant registries (see 3.8).
- **Sync metadata is authenticated** with a per-vault HMAC-SHA-256 seal, so a malicious
  cloud/account can no longer roll back, delete, or brick records (see 3.6).
- **Master password is never entered in-page**: unlock moved to the toolbar popup / app
  window only (see 3.7).
- **Passkey signing hardened**: the app signs only a well-formed WebAuthn assertion whose
  authData binds SHA-256(rpId), never arbitrary bytes.
- **Autofill redirect boundary**: cross-domain redirect targets are no longer treated as
  same-site for credential release.
- Export CSV **formula/DDE injection** neutralised; vault parsing bounded against
  oversize/deserialisation DoS; a single poison record is tolerated on read.
- **Mobile autofill target verification** (Android): fuzzy brand/name matching removed; web
  fills require an exact registrable-domain match and a browser-verified web domain, native
  fills require an exact stored package association (see 3.10).
- **Mobile sync anti-downgrade**: the document-integrity seal is now enforced on every mobile
  unlock/merge with an app-private "already protected" marker (see 3.6, 3.10).
- **Mobile clipboard hygiene**: recovery codes and the accessibility paste fallback go through
  the sensitivity-flagged, auto-clearing clipboard path.
- **Mobile biometric crypto-gate shipped and verified on-device**: Android BiometricPrompt +
  CryptoObject with enrollment invalidation (plus a runtime hardware probe with a safe
  fallback), iOS BiometryCurrentSet; background-safe clipboard clearing via ClearPrimaryClip;
  the vault now locks when the app is closed and after 1 minute in background.

- Quick unlock on Windows moved from a DPAPI‑only cache (readable by any same‑user
  process, and non‑expiring when auto‑lock was off) to **Windows Hello / TPM**
  wrapping with per‑install entropy and a hard expiry ceiling.
- LAN relay: **private‑range peer allow‑list**, header‑based token, and
  `GET /clip` off by default.
- WebAuthn: **rpId is now validated** against the page origin before any vault access.
- Google OAuth **client secret removed from source**; loaded from env / git‑ignored
  file at runtime.
- Diagnostic logs no longer contain clipboard/SMS content or IPC response bodies.
